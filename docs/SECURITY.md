# Security

## Security invariants (and where they are enforced)

| Invariant | Enforcement |
|---|---|
| Never trust an agent's self-reported identity | `AuthGuard.authenticateAgent`: Ed25519 signature against registered key |
| Never trust an agent's claim that a human approved | Approval only via human-only routes; engine reads approval state from DB |
| Agent can't modify its permissions / raise limits | Delegation, policy and supplier routes are `@Human(...)` |
| Agent can't approve its own transaction | Approval routes are human-only; `@FreshAuth(900)` |
| Authorization can't be reused for a different transaction | Token binds fingerprint + all fields; gateway compares stored intent and expected params |
| Concurrent transactions can't overspend | Agent row lock + reservations in one DB transaction |
| No payment without an enforceable authorization | Gateway is the only payment path; consumes atomically |
| No payment credentials or signing secrets reach the LLM | Agent SDK holds only the agent's own signing key; provider credentials live in the gateway |
| LLM output is never final authority | Deterministic `evaluatePurchase` |
| Fail closed | Missing policy/rules → DENY; errors → no authorization; unknown access rule → 403 |
| External content is untrusted | Agent-supplied payee details are compared, never trusted; gateway pays verified counterparty |
| No cross-organization access | All reads/writes scoped by org from credentials; 404 for foreign ids |

## Cryptography

Only standard algorithms through Node's `crypto` module. No custom primitives.

| Use | Algorithm |
|---|---|
| Agent request signatures | Ed25519 (RFC 8032) over `scheme, method, path, timestamp, nonce, sha256(body)` |
| Authorization tokens | Compact JWS (RFC 7515), `alg: EdDSA` (RFC 8037), algorithm pinned on verify |
| Audit events | SHA-256 hash chain + Ed25519 signature over each event hash |
| Payee fingerprints | HMAC-SHA256 with server-side pepper (bank numbers are low-entropy) |
| Transaction fingerprint | SHA-256 over canonical JSON (sorted keys, integers only) |
| Dev human tokens | HMAC-SHA256 JWT (development only; disabled in production by config) |

## Data handling

- Raw bank account numbers are **not stored**: only HMAC fingerprint, type and last 4 digits.
- No card numbers, no customer funds, no money transmission. The sandbox adapter moves no money.
- Secrets live in `.env` locally (gitignored, generated by `pnpm setup:env`); production must use a secret
  manager and a KMS-backed `Signer`.

## Known gaps before any production use

See [THREAT_MODEL.md § Residual risks](THREAT_MODEL.md#residual-risks-unresolved-documented). In short: real
OIDC, KMS-held keys, external audit anchoring, Postgres RLS, bank-ownership verification at onboarding,
production payment adapters with reconciliation, distributed rate limiting, nonce cleanup, independent
security review and penetration test, and legal/compliance review.

**This MVP is not production-certified, compliant, or independently audited.**

## Reporting

Report suspected vulnerabilities privately to the maintainers; do not open public issues.
