# ADR-0002: Identity, authorization tokens and enforcement

- **Status:** Accepted
- **Date:** 2026-10-22

## Context

The product's value depends on an agent being unable to pay anything a human did not authorize, even if the
agent is compromised. Self-declared agent identity, bearer API keys and "advisory" decisions are insufficient.

## Decision

1. **Agents authenticate with per-request Ed25519 signatures** (key pair generated by the customer; we store
   only the public key). Signatures cover method, path, timestamp, nonce and body hash; nonces are single-use.
   Chosen over bearer API keys because a leaked request cannot be replayed or modified, and over mTLS for
   ease of use across agent runtimes. The format is close to RFC 9421 to ease migration.
2. **Authorizations are compact JWS (EdDSA)** binding a SHA-256 transaction fingerprint and every
   transaction field, with a 10-minute expiry and a nonce. Algorithm is pinned on verification.
3. **Enforcement lives in our gateway**, the only holder of payment credentials. It verifies the token,
   matches the caller and exact parameters, re-checks live state, and consumes the authorization atomically
   in PostgreSQL before calling the provider (idempotency key = authorization id).
4. **Humans authenticate via OIDC** (dev HMAC issuer locally, disabled in production) and are the only
   principals allowed to change authority (delegations, policies, suppliers) or approve.
5. **Payee verification uses HMAC fingerprints** of normalized bank details with a server-side pepper; raw
   account numbers are not stored.

## Consequences

- Customers must route agent payments through AgentTrust (or an adapter we provide) for guarantees to hold.
- Platform key custody is critical: production requires KMS-backed signing and rotation (tracked as R1).
- A future single-use virtual-card adapter can provide network-level enforcement in addition to our gateway.
